#### R-05 详细说明

**问题**：V1.0/V1.1 设计中，自建了 `RagOrchestrationService` 来编排五个 RAG 阶段，以及 `QueryProcessor`、`DocumentGenerator` 等自定义接口。实际上 Spring AI 的 `RetrievalAugmentationAdvisor` 已经通过以下接口提供了等价能力：

| 自定义组件（已删除） | Spring AI 等价接口 | 说明 |
|-------------------|-------------------|------|
| `RagOrchestrationService` | `RetrievalAugmentationAdvisor` | Spring AI 内置的 RAG 编排 Advisor |
| `QueryProcessor` (自定义) | `QueryTransform` (Spring AI) | 查询预处理接口 |
| `DocumentGenerator` (自定义) | `ChatClient` (Spring AI 内置) | 流式生成由 ChatClient 原生支持 |
| `ContextAugmentor` (自定义) | `DocumentAugmentor` (Spring AI) | 上下文增强接口 |
| `DocumentPostProcessorChain` (自定义) | 自动注入 `List<DocumentPostProcessor>` (Spring AI) | Spring 按 @Order 排序注入 |

**影响范围**：
- 5.1 节全部重写：架构图、代码示例、扩展点表
- 5.2 节 AgentCommandFacadeImpl 改为注入 `ChatClient.Builder` + `RetrievalAugmentationAdvisor`
- 8.1 节时序图更新：去掉自定义的 5 个委托调用层，简化为 ChatClient → Advisor 内部编排
- 8.2 节活动图更新：编排器由 `RagOrchestrationService` 改为 `ChatClient + RetrievalAugmentationAdvisor`
- 8.3 节多轮对话时序图同步更新
- 附录 A/B 同步调整

## 3. 设计决策记录（ADR — Architecture Decision Records）

以下为评审过程中产生的重要架构决策，共 5 项：

### ADR-001（已更新）：RAG 模块化架构基于 Spring AI RetrievalAugmentationAdvisor

- **迭代历程**：
  - V1.0：使用 `QuestionAnswerAdvisor` 黑盒模式
  - V1.1：改为自建 `RagOrchestrationService` 编排五个自定义接口（QueryProcessor / DocumentRetriever / DocumentPostProcessor / ContextAugmentor / DocumentGenerator）
  - **V1.2（当前）**：**直接使用 Spring AI 的 `RetrievalAugmentationAdvisor`**，自定义组件仅需实现 Spring AI 提供的标准接口（`QueryTransform`、`DocumentRetriever`、`DocumentPostProcessor`、`DocumentAugmentor`），由 Advisor 负责编排
- **决策理由**：Spring AI 已通过标准接口提供了完整扩展点，不需要自己写编排器。需要自定义的部分通过实现接口并声明为 Bean 即可，Spring 自动注入责任链
- **影响**：代码量减少（删除了 `RagOrchestrationService`、`QueryProcessor`、`DocumentGenerator` 三个自定义接口，以及 `ContextAugmentor`、`DocumentPostProcessorChain` 两个自定义组件），改为直接使用 Spring AI 的等价接口和自动装配能力

### ADR-002：Facade 层 userId 放入 Request 对象而非单独参数或 Session

- **决策**：POST 场景（AskQuestionRequest / FeedbackRequest）userId 作为 Request 对象的 `@NotBlank` 字段，Controller 从 HTTP Header 提取后注入
- **理由**：调用方与 HTTP 协议解耦（MQ/定时任务可直接构造）；方法签名简洁，参数内聚
- **例外**：GET 场景（`getConversation`）无 Request body，userId 保持独立参数

### ADR-003：基础设施 Bean 尽量依赖 Spring AI auto-config

- **决策**：ChatModel、EmbeddingModel、VectorStore、ChatClient.Builder 均通过 yaml 驱动自动创建；仅 ChatMemory 因无 Redis 版 auto-config 需手动 @Bean
- **理由**：减少样板代码，自动享受版本升级红利，避免手动/自动 Bean 冲突
- **影响**：配置集中在 yaml，团队可读性提升；但需要确保 yaml key 与 Spring AI 版本匹配

### ADR-004：去掉 message_count 冗余字段

- **决策**：agent_conversation 表不维护 message_count 冗余字段；前端需要时由应用层执行 `SELECT conversation_id, COUNT(*) GROUP BY` 二次查询
- **理由**：写多读少场景下，每条消息多一次 UPDATE 的代价高于列表页多一次 5ms 的 COUNT 查询。MVP 阶段 20 条/页规模下双查询方案足够
- **回退条件**：单用户对话量破万、列表页响应超过 50ms 时，可重新引入冗余字段或 Redis 计数器

### ADR-005：ES metadata 使用 flattened 类型

- **决策**：不逐字段定义元数据映射，使用 `flattened` 类型统一承载
- **理由**：不同文档类型的元数据 key 各不相同，`object` 会导致 mapping 爆炸，`flattened` 将所有叶子值索引为 keyword 且不膨胀映射
- **代价**：数值类元数据无法范围查询——可接受，元数据主要用于过滤和高亮，非排序和聚合
